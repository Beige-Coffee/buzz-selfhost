# Push notifications on a self-hosted relay, through Block's gateway

- **When:** 2026-10-23, 16:41 to 17:12 PDT, about 31 minutes from creating the droplet to deleting it.
- **Question:** can a self-hosted relay wake the Buzz app from the App Store (0.25, released
  2026-10-21) through Block's push gateway at push.buzz.xyz? block/buzz#5206 (no push for
  self-hosted relays) was still open, and Block marks push experimental (`docs/buzz-push.md`).
- **Setup:** one DigitalOcean droplet, Ubuntu 24.04 x86 with 4 GB (s-2vcpu-4gb), in sfo2 because
  sfo3 had none of that size free, at `<ip>.sslip.io`. The skill's server mode with phone pairing,
  through `tests/smoke-vps.sh install`. Then one change in the bundle's `.env`,
  `BUZZ_PUSH_ENABLED=true`, keeping the bundle's own
  `BUZZ_PUSH_GATEWAY_DELIVERY_URL=https://push.buzz.xyz/v1/deliveries/apns`, and
  `BUZZ_COMPOSE_TLS=true ./run.sh restart`. The owner joined from Buzz 1.0 on a computer, created
  `general`, paired an iPhone with Buzz 0.25 from the App Store, and locked it. A test identity,
  made on the operator's computer and added with `./run.sh add-member`, then sent three messages a
  minute apart.
- **Relay version:** `sha-e8781ca` (relay 0.2.1), the skill's tested image.
- **Result:** push works from this self-hosted relay to the App Store app.
  - The install passed 31 of 31, and check-relay.sh passed every line with push on.
  - After the restart, NIP-11 listed `buzz-push-v1` and a `push` descriptor at once. The relay
    makes the community for `RELAY_URL`'s host at its first start, so nobody had to join first.
  - The phone published its lease (kind 30350) at 16:49:15, half a minute after the owner created
    `general`. The lease held a grant from the gateway, and the gateway's answers below show the
    grant was good.
  - The three sends, and what the owner saw on the locked phone:

    | Sent (PDT) | Message | Relay | Gateway | On the phone |
    |---|---|---|---|---|
    | 16:53:50 | (a) A DM, opened the way the app opens one (kind 41010), then kind 9 with `h` the DM and `p` the owner | matched the lease, queued a wake | accepted, in 0.25 s | a notification with the message's text |
    | 16:54:50 | (b) A mention in `general`: kind 9 with `h` `general` and `p` the owner | matched, queued a wake | accepted, in 0.10 s | a notification with the message's text |
    | 16:55:50 | (c) The control, plain in `general`: kind 9 with `h` only | no match, no wake | no call | a notification with the message's text (see Notes) |

  - "Accepted" is the relay's `accepted` outcome: a success answer with `{"status":"accepted"}`,
    which the gateway's protocol (NIP-PL) defines as 200, APNs accepted. Both wakes went on the
    first attempt. The relay logged no push warning or error.
- **Cost:** about $0.02, 31 minutes at $0.0357 an hour ($0.036 if DigitalOcean bills the whole hour).
- **Removed:** the droplet (the API answered 204, then 404 for it), its tag, and the test
  identity's key. No SSH key was added: the account's existing key for the operator's computer
  was used.

## Notes

- Each notification showed the message's text, not the gateway's fixed "Reconnect to your relay
  now". NIP-PL says the app's Notification Service Extension replaces that text when it can read
  the message. The relay's log shows the owner's key querying the relay within 4 seconds of each
  send, but Buzz 1.0 on the owner's computer uses the same key, so the log can't say which device
  asked.
- (c) is what the owner observed; its cause is unconfirmed. The relay sent no wake for it, since
  the lease doesn't cover `general` (next note). It showed about 60 seconds after (b)'s wake, and
  the likely cause, that the app was still awake from that wake, is unconfirmed. In the relay's
  log, the phone's WebSocket, the one that published the lease, closed at 16:49:26, and the
  owner's key opened no other until 17:02:34. The one open meanwhile dates from 16:47:55, when the
  owner joined from Buzz 1.0 on the computer. The owner's key sent `/query` requests at 16:55:50
  and 16:55:53, which can't be told apart from the computer's: that key also queried in a batch
  every minute, at :55, all through the test.
- What the lease covers, as the app's source says
  (`mobile/lib/shared/push/push_subscription_provider.dart`): kinds 9, 40002, 45001 and 45003 that
  p-tag the owner, except the owner's own, and kind 9 in each DM the app knows of. Channels such as
  `general` are never in it, so a plain channel message gets no wake. The app puts a `p` tag for
  each recipient on a DM message, so (a) woke the phone through that, though the locked app hadn't
  added the new DM to its lease. When the owner opened the app at 17:02, it published generation
  2, with the DM added.
- The relay logs nothing for a delivered wake, nor for a 4xx from the gateway: only startup lines
  and some failures, such as a 410 from the gateway or a suppressed wake. The outcome is in its
  metrics (`buzz_push_deliveries_total` by outcome, on the metrics port inside the container) and
  in `push_wake_outbox` (state, attempts). `push_leases` has an `endpoint_grant` column holding the
  gateway's grant, so the queries below never select it.
- The skill's Phones paragraph (SKILL.md section 4) says a self-hosted relay can't send push to the
  App Store app (block/buzz#5206). This run shows it can, on `sha-e8781ca` with
  `BUZZ_PUSH_ENABLED=true`. The skill isn't changed here.
- The gateway's configuration (`crates/buzz-push-gateway/src/config.rs` at `e8781ca`) has no
  setting for allowed relays. A grant is bound to the relay key the phone delegates to, here the
  relay's own key, named in its NIP-11 `push.keys` and as `self`, which signs each delivery.

### 4. The lease and the channels, before the sends, 16:51 PDT

The query, read-only, never selecting `push_leases.endpoint_grant` or any event's content:

```sql
-- Read-only view of push state and channels. Never selects push_leases.endpoint_grant or event content.
SET default_transaction_read_only = on;
\pset pager off
\echo == push_leases (endpoint_grant not selected)
SELECT CASE WHEN encode(author,'hex') = :'owner' THEN 'owner' ELSE 'other:' || left(encode(author,'hex'),8) END AS author,
       installation_id, generation, active, endpoint_enabled, endpoint_hash IS NOT NULL AS has_endpoint, max_class,
       to_timestamp(source_created_at) AS lease_created, to_timestamp(expires_at) AS expires, updated_at,
       jsonb_array_length(subscriptions) AS subs
FROM push_leases ORDER BY updated_at;
\echo == lease subscriptions
SELECT jsonb_pretty(subscriptions) FROM push_leases WHERE subscriptions IS NOT NULL;
\echo == kind 30350 events (public tags only)
SELECT encode(pubkey,'hex') = :'owner' AS from_owner, created_at, received_at, d_tag, tags FROM events WHERE kind = 30350 ORDER BY created_at;
\echo == channels
SELECT id, name, channel_type, visibility, created_at, encode(created_by,'hex') = :'owner' AS by_owner FROM channels WHERE deleted_at IS NULL ORDER BY created_at;
\echo == channel members
SELECT c.name, c.channel_type, CASE WHEN encode(m.pubkey,'hex') = :'owner' THEN 'owner' ELSE left(encode(m.pubkey,'hex'),8) END AS member, m.role, m.removed_at IS NOT NULL AS removed
FROM channel_members m JOIN channels c ON c.id = m.channel_id AND c.community_id = m.community_id ORDER BY c.created_at, m.joined_at;
\echo == push_wake_outbox
SELECT CASE WHEN encode(author,'hex') = :'owner' THEN 'owner' ELSE left(encode(author,'hex'),8) END AS author, lease_generation, encode(event_id,'hex') AS event_id, class, state, attempts, created_at, next_attempt_at
FROM push_wake_outbox ORDER BY created_at;
\echo == push_match_queue
SELECT encode(event_id,'hex') AS event_id, state, attempts, created_at FROM push_match_queue ORDER BY created_at;
```

# post.sh <kind> <tags-json> [content]: sign an event as the test identity and POST it to the relay's
